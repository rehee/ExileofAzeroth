## 1. 结论

**方案 T 可行，进入正式开发。** 验证阶段的两个风险都已排除：

| 风险 | 结果 |
|------|------|
| 1. DQQ 能否在普通 .NET 进程里运行 | ✅ DQQ.Web.Component 的 service 在控制台程序里以在线模式工作（登录、角色、录像、战斗），**DQQ 源码零改动**。只需替换三处浏览器依赖：`IClientRepository`（内存实现）、`NavigationManager`、`IJSRuntime`。 |
| 2. benilla 能否不连 WoW 服务器、由 runtime 驱动 | ✅ 桥接模块把 runtime 的 JSON 消息合成为客户端原有的 `SessionEvent`，客户端其余部分（模型、动画、镜头、加载画面、FrameXML、插件）照常工作。 |

完整流程已跑通，并经用户手动验收：
1. 自动登录，跳过领域选择，进入选人画面（DQQ 角色，人类女性）。
2. 进入北郡，自由模式，WoW 默认操作。
3. 打开插件的 Replays 窗口：显示服务器录像列表和录像文件列表。
4. 点一条录像：显示加载画面并传送到战场；开场等模型都显示后才开战；按 30 tick/s 演出战斗。
5. 战斗结束后清场，传送回北郡，交还操作。

## 2. 做法（与架构文档的对应）

| 部分 | 做法 | 位置 |
|------|------|------|
| runtime | .NET 8 控制台程序，只引用 `source/dqq/` 里的 DLL；自写 WebSocket 服务（无 ASP.NET）；`MessageRouter` 把 `ui.*` 转给 DQQ service | `src/Exile.Runtime/` |
| 节奏 | DQQ 自带的节流在 Windows 上每 tick 约 45 ms（计时精度 15.6 ms），改为 `SkipDelay` + 自己的 `TickPacer` + `timeBeginPeriod(1)` | `Combat/TickPacer.cs` |
| 客户端桥接 | `net/exile.rs`：替代 `spawn_net` 的网络线程，合成登录、领域、角色列表、进世界、单位创建与移动、血量、攻击、插件消息等事件 | `client/crates/benilla-app/src/net/exile.rs` |
| 界面 | Lua 插件 `ExileUI`，经 WoW 插件消息（`SendAddonMessage` / `CHAT_MSG_ADDON`）与桥接通信，桥接再转成 runtime 的 `ui.*` | `addons/ExileUI/`，协议 §5 |
| 录像文件 | 与 DQQ 网页版导出、导入同一格式（`CombatReplayEntity` 的 JSON 再 Base64） | `Replays/ReplayFiles.cs` |

对上游 benilla 的改动保持很小：除了新文件 `net/exile.rs`，只改了 8 个文件、约 70 行，全部只在 Exile 模式（设置了 `EXILE_RUNTIME`）下生效。

| 文件 | 改动 |
|------|------|
| `net.rs`、`net/io.rs`、`Cargo.toml` | 接入桥接模块；Exile 模式标志 |
| `loading_screen.rs` | 加载画面至少显示 0.5 秒 |
| `player/camera.rs` | 回放期间镜头不自动转回、右键只转镜头 |
| `creature_anim/select.rs` | 回放期间走跑动作按标准速度播放 |
| `ui_chat/net.rs`、`ui_chat/feed.rs` | 不上聊天显示锁（见 §3） |

## 3. 踩过的坑

| 问题 | 原因 | 解决 |
|------|------|------|
| 自由模式不能移动、不能转视角、Esc 无效 | 按键绑定属于账号数据，客户端要等服务器发来账号数据摘要才加载 | 进世界时补发全空的 `AccountDataMd5` |
| 插件收不到回复；聊天框从来没有内容 | 客户端在会话开始、每次离开世界时锁住聊天显示，等进世界的初始化流程放开；桥接流程下一直没放开 | Exile 模式下不上锁 |
| 插件消息要等发送者名字 | `CHAT_MSG_ADDON` 要先解析发送者名字 | 桥接应答 `NameQuery` |
| 单位不动 | `MonsterMove` 的路径要以起点开头，只给终点时客户端不装样条 | 发 `[起点, 终点]` |
| 移动动画断断续续 | 每帧一条 40 ms 的样条，步子不均匀时动画在站立和走之间切换 | 每步收到即发、移动时间略长于一帧，起步时拉长到第 5 帧，前后衔接（最初是延后 5 帧显示，2026-11-07 改为不缓冲） |
| 跑步动作极慢 | 客户端按实际速度缩放动作，DQQ 单位每秒只走约 1 码 | 战斗中行走速度设为 0.05（一律跑步），回放期间动作按标准速度 |
| 单位悬空 | 生物高度本来由服务器给 | 桥接读取战场附近 ADT 地形取地面高度 |
| 模型还没出来战斗已开打 | 模型加载需要 1~2 秒 | 开场等待：runtime 发完开场帧后等客户端 `combat.ready` |
| 朝向始终为 0 | DQQ 只给投射物设 `Angle` | 移动时朝移动方向，站立时朝 DQQ 目标坐标 |
| 回放结果与原记录不一致（个别旧录像） | 10-30 的录像在当前 DQQ 下重放结果不同，推测 DQQ 逻辑之后有改动；录像里 `GameVersion` 为空 | 已知遗留，**不处理**（用户 2026-11-07 确认） |

开发环境方面：AI 在 Windows 上只能用资源管理器双击 `tools/run-*.cmd`，结果看 `tools/logs/`；中文输入法会截走游戏按键；AI 的模拟点击有时点不中插件按钮（用户手点正常）。详见 `docs/dev-workflow.md`。

## 4. 性能数据

| 项 | 结果 |
|----|------|
| 后台模式（不等待）一整场 900 tick | 约 2.8 秒 |
| 观看模式推送节奏 | 平均 33.32 ms/tick，p99 33.43 ms |
| WebSocket 发出 → 收到 | 平均 0.67 ms，p99 5 ms |
| 渲染帧大小 | 平均约 11 KB，最大约 15 KB（JSON） |
| 一场 900 tick 的 GC 暂停 | 合计约 40~50 ms（Gen2 1~2 次），观看时无可见卡顿 |
| 客户端移动指令 | 5 帧一段后，一场约 1200 条（原每帧一条约 5600 条） |

结论：WebSocket + JSON 够用（D9 不变），暂不需要二进制编码或缓冲。

## 5. 对架构文档的修订

已随实现写入 `architecture.md` 的：D27–D29（自由模式、回放模式、回放期间操作与镜头）；§5.2 的坐标（1 单位 2 码、贴地、朝向、5 帧一段、跑步动画、体型、开场等待、战斗姿势、原版阴影）。

还需要修订或确认的：
1. **§7 benilla 不连服务器运行**：改写为实际做法（桥接模块合成 `SessionEvent`，见本文 §2），不再写"验证阶段确认"。
2. **§4 藏身处的界面调用**：插件不直连 runtime，经 WoW 插件消息由桥接转发（协议 §5）；消息格式是 `verb;参数`，不是 JSON。
3. **§8 安装目录**：开发版客户端的状态和插件在 `benilla-config/`（插件在 `benilla-config/AddOns/`），发布版在客户端旁边；启动器要把插件放到这里，而不是 WoW 的 `Interface/AddOns`。
4. **D18 中文显示**：已确认 enUS 字体没有中文字形（中文名显示为空白），附带中文字体的工作要排进界面计划。
